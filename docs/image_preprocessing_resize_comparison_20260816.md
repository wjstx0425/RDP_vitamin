# 图像预处理方案对比：中心裁剪与完整画面直接拉伸

日期：2026-08-16
用途：讨论并确定训练数据与部署输入应采用的统一图像几何处理方式

## 1. 讨论范围

本文只比较下面两种 resize/crop 方案：

- 方案 A：保持宽高比缩放，然后中心裁剪成正方形。
- 方案 B：保留完整画面，直接拉伸成正方形。

共同输入是一张从三联相机中切出的 `1280×800` panel，目标输出为
`224×224` 或 `256×256`。颜色通道转换、触觉图像旋转、鱼眼 mask、时间同步
和相机左右映射不属于本文讨论范围；这些处理应在选定几何方案后单独保持一致。

## 2. 先给出结论

对于一个已经训练完成的 checkpoint，首要原则不是选择“看起来更自然”的方案，
而是让部署预处理与该 checkpoint 的训练预处理完全一致。

- 如果训练数据使用方案 B，则当前 checkpoint 部署时也应使用方案 B。仅在部署侧
  改成方案 A 会引入输入分布偏移，并丢失约 37.5% 的水平内容。
- 如果训练数据使用方案 A，则部署也应使用方案 A。部署侧单独改成方案 B 会引入
  训练时不存在的非等比形变。
- 如果要为下一版数据重新选择方案，应分别用匹配的训练和部署预处理做完整 A/B
  实验，不能只替换部署代码后比较机器人表现。

当前可见的 Vitamin-B 数据处理脚本使用方案 B，默认输出 `224×224`。因此针对由
该数据链路训练的现有 RDP checkpoint，推荐继续采用方案 B。关于普通 SmolVLA
`256×256` checkpoint，仍需要核对它实际使用的数据集 metadata 或训练 transform，
不能只根据当前部署分辨率推断其训练方式。

## 3. 两种方案的流程

### 3.1 方案 A：等比缩放后中心裁剪

处理流程：

```text
1280×800 panel
    ↓ 保持宽高比缩放，以目标正方形的高度为准
中间图像（359×224 或 410×256）
    ↓ 水平方向中心裁剪
224×224 或 256×256
```

对应的核心逻辑是：

```python
scale = output_height / input_height
resized_width = ceil(input_width * scale)
resized = cv2.resize(
    image,
    (resized_width, output_height),
    interpolation=cv2.INTER_AREA,
)
start_x = (resized_width - output_width) // 2
output = resized[:, start_x : start_x + output_width]
```

当前通用实现位于 `utils/common/cv2_util.py:85-123`。对于这里讨论的下采样，
它使用 `cv2.INTER_AREA`，并且执行顺序是“先缩放，后裁剪”，不是先在原始图上
直接切出 `800×800` 再缩放。两者几何范围接近，但由于插值和取整，像素结果并不
完全相同。

精确离散计算如下：

| 输入 → 输出 | 中间图像 | 中心 crop 范围 | 中间图水平保留 | 中间图水平丢失 |
|---|---:|---:|---:|---:|
| `1280×800 → 224×224` | `359×224` | `[67:291)` | `224/359 = 62.3955%` | `37.6045%` |
| `1280×800 → 256×256` | `410×256` | `[77:333)` | `256/410 = 62.4390%` | `37.5610%` |

可以把它概括为：保留原始 panel 中间约 62.5% 的水平范围，丢失约 37.5%，
即左右各丢约 240 个原始输入像素。`224×224` 情况因为向上取整后需要裁掉奇数
列，实际在中间图上是左侧 67 列、右侧 68 列，并非严格对称。

优点：

- 横向和纵向使用同一个缩放比例，物体宽高比保持不变。
- 圆形仍接近圆形，几何形状更自然。
- 当任务目标始终位于画面中央时，模型可以获得更高的中心区域有效采样密度。

缺点：

- 约 37.5% 的水平内容被删除，左右边缘的物体、机械臂或触觉特征可能完全消失。
- 如果训练数据使用完整画面直接拉伸，该方案会造成明显的训练/部署分布偏移。
- “水平范围保留比例”只是像素跨度的近似，不等价于经过相机标定计算出的真实
  光学视场角。

### 3.2 方案 B：完整画面直接拉伸

处理流程：

```text
1280×800 panel
    ↓ 横向和纵向分别缩放到目标尺寸
224×224 或 256×256
```

对应的核心逻辑是：

```python
output = cv2.resize(
    image,
    (output_width, output_height),
    interpolation=cv2.INTER_LINEAR,
)
```

Vitamin-B 数据处理代码在
`VB-VLA/Data_collection/vitamin_b_data_collection_pipeline/01_crop_img.py:102-128`
先切出三个完整 panel，再对每个 panel 直接调用 `cv2.resize`。该调用没有显式传入
插值参数，因此 OpenCV 使用默认的 `INTER_LINEAR`。脚本和当前可见配置的默认
目标分辨率均为 `224×224`。

当前主部署在 `real_world/bimanual_umi_env.py:25-39` 使用显式
`cv2.INTER_LINEAR` 实现相同几何处理，visual 和两个 tactile panel 都复用该逻辑。
`tests/test_camera_frame_preprocessing.py` 使用左右边缘标记对实际相机 transform 做
逐像素回归，保证完整水平画面没有再次被中心裁剪。

形变计算如下：

| 输入 → 输出 | 横向缩放比例 | 纵向缩放比例 | 相对形变 |
|---|---:|---:|---:|
| `1280×800 → 224×224` | `224/1280 = 0.175` | `224/800 = 0.280` | 纵向相对横向为 `1.6×` |
| `1280×800 → 256×256` | `256/1280 = 0.200` | `256/800 = 0.320` | 纵向相对横向为 `1.6×` |

因此圆形会变成高宽比约为 `1.6` 的竖椭圆。也可以描述为：纵向相对横向放大
60%，或横向相对纵向压缩 37.5%。从 224 改为 256 会增加采样点数量，但不会
消除这种几何形变。

优点：

- 保留 100% 的原始水平和垂直画面，不删除边缘内容。
- 实现简单，所有 panel 使用同一确定性变换。
- 与当前可见的 Vitamin-B `224×224` 数据处理链路一致。

缺点：

- 不保持物体宽高比，会产生固定的非等比形变。
- 如果 checkpoint 是用等比中心裁剪数据训练的，该方案同样会造成分布偏移。
- 对依赖精确二维几何形状的模型，形变可能增加学习难度。

## 4. 核心对比

| 对比项 | 方案 A：等比缩放＋中心裁剪 | 方案 B：完整画面直接拉伸 |
|---|---|---|
| 是否保持宽高比 | 是 | 否 |
| 水平内容保留 | 约 62.4% | 100% |
| 水平内容丢失 | 约 37.6% | 0% |
| 几何形变 | 基本无非等比形变 | 纵横相对比例为 1.6× |
| 当前实现的插值 | 下采样使用 `INTER_AREA` | 使用 `INTER_LINEAR` |
| 边缘目标 | 可能被完全裁掉 | 保留但发生形变 |
| 中央目标采样密度 | 较高 | 较低 |
| 与当前可见 RDP 训练数据一致性 | 不一致 | 一致 |
| 适合直接用于现有 RDP checkpoint | 不推荐 | 推荐 |
| 若用于新数据集 | 必须训练和部署同时采用 | 必须训练和部署同时采用 |

两种方案实际上是在交换两个属性：

- 方案 A 牺牲水平视野，换取几何比例不变。
- 方案 B 牺牲几何比例，换取完整视野。

不存在脱离任务、数据和 checkpoint 的绝对最优方案。

## 5. 当前代码与数据状态

截至 2026-08-16，当前工作区能确认的状态是：

1. 通用 helper `utils/common/cv2_util.py:get_image_transform` 实现方案 A。
2. 历史部署曾调用该 helper 对 visual 和 tactile panel 做中心裁剪。
3. 当前 tracked 主部署已经改为方案 B，不再调用该通用 helper。
4. 当前 RDP 部署输入为 `224×224`，普通 SmolVLA 部署输入为 `256×256`。
5. 当前可见 Vitamin-B 数据脚本和 YAML 配置默认使用 `224×224` 方案 B。
6. 当前证据足以支持“RDP 224 的训练与部署几何一致”；不足以单独证明普通
   SmolVLA 256 checkpoint 的真实训练 transform，需要继续查 checkpoint 对应的
   dataset metadata 或训练配置。

注意：本机的 `VB-VLA/` 当前是未跟踪参考目录。讨论时可以把其中的数据脚本作为
本地代码证据，但在正式发布结论前，仍应记录对应训练仓库的 commit、数据集版本和
checkpoint 标识，避免以后目录内容变化导致证据漂移。

## 6. 建议的决策流程

### 6.1 针对现有 checkpoint

1. 找到 checkpoint 对应的数据集版本和训练配置。
2. 确认训练 sample 在送入模型前究竟使用方案 A 还是方案 B。
3. 部署严格复现训练方案，包括 crop 顺序、输出分辨率和插值方法。
4. 如果无法确认训练方案，不要根据预览图观感直接修改真实机器人部署；应先恢复
   metadata，或对训练数据中的已保存模型输入做像素级对照。

针对当前已确认的 RDP 224 数据链路，第 2 步的答案是方案 B，因此现有 checkpoint
建议使用方案 B。

### 6.2 针对下一版数据或重新训练

如果团队希望重新判断哪种几何方式更适合任务，应让两组实验分别保持训练/部署
一致：

- 实验 A：方案 A 数据训练的 checkpoint，使用方案 A 部署。
- 实验 B：方案 B 数据训练的 checkpoint，使用方案 B 部署。

不要用“方案 B 训练的 checkpoint + 方案 A 部署”与“方案 B 训练 + 方案 B 部署”
来判断方案 A 的好坏，因为前者同时混入了预处理分布偏移。

## 7. 推荐验证实验

### 7.1 纯视觉检查

从同一批原始 `1280×800` panel 生成 A/B 两套无损 PNG，并至少包含：

- 带圆形或棋盘格的标定画面，用来观察 1.6× 非等比形变；
- 左右边缘有明显标记或任务物体的画面，用来观察约 37.5% 的裁剪损失；
- 机械臂分别位于中央和边缘的真实任务画面；
- visual、左 tactile、右 tactile 三类 panel。

需要记录的不只是“哪张更好看”，还包括：

- 左右边缘目标是否可见；
- 目标包围框是否被截断；
- 圆形或已知尺寸标记的高宽比；
- 中央区域每个目标占用的输出像素数量。

### 7.2 离线模型检查

固定机器人 state 和原始相机帧，只改变 A/B 图像预处理，然后比较：

- 模型输出动作的均值、方差和两方案差值；
- 是否出现非有限值或安全阈值越界；
- 目标位于中央与左右边缘时的动作差异；
- 多帧连续输入下动作是否稳定。

该实验只能说明 checkpoint 对输入变换是否敏感，不能单独证明哪种方案更适合重新
训练后的模型。

### 7.3 匹配训练的正式 A/B 实验

使用同一批原始示范、相同划分、相同训练超参数和随机种子，仅改变预处理方案。
测试集需要按目标位置分层：中央、左边缘、右边缘。建议主要指标为：

- 总任务成功率；
- 中央目标成功率；
- 左右边缘目标成功率；
- 接触或抓取位置误差；
- 安全拒绝率和动作跳变；
- 不同随机种子下的均值和置信区间。

只有这种实验才能公平比较方案 A 与方案 B 本身。

## 9. 建议记录的最终数据契约

团队决定后，不要只写“resize 到 224”或“crop 成方形”，应固定完整契约：

```text
输入 panel 尺寸：1280×800
处理方案：A（等比缩放＋中心裁剪）/ B（完整画面直接拉伸）
操作顺序：________________
输出尺寸：________________
插值方法：________________
颜色通道：________________
数值类型和范围：________________
触觉方向规则：另见独立契约
训练代码 commit：________________
部署代码 commit：________________
数据集版本：________________
checkpoint：________________
```

预处理是 checkpoint 输入契约的一部分。最终选择一旦确定，应同时写入数据转换、
训练配置、部署配置和自动化回归测试，避免以后再次出现“训练画面”和“部署画面”
不一致。
